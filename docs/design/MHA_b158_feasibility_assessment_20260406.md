# Zen-Claw 中 MHA / b1.58 三种方案可行性评估（2026-04-06）

## 1. 评估基线：当前 zen-claw 的技术现实

> 本评估不是抽象论文讨论，而是基于当前仓库“已落地能力 + 代码组织方式”判断。

当前项目已经具备三类与本题高度相关的基础：

1. **运行时分层与门控**：已有 Gate1/Gate2/Gate3 路由分层，且把“执行决策”与“规划决策”分离成结构化契约（`RoutingDecision` / `ExecutionIntent`）。
2. **可切换记忆召回**：`ContextBuilder` 已支持 `none/sqlite/rag/keyword` 等 recall 模式，并可在不可用时降级，说明“检索策略可插拔”。
3. **工具安全与审批闭环**：`ToolPolicyEngine` + `ApprovalGate` + kill-switch 已把最终执行层做成独立安全面，具备“最后一跳硬约束”的工程条件。

换言之，zen-claw 现在更像“可组合控制系统”，不是单段式聊天机器人。这决定了你给出的三种方案都不是从 0 开始，但**落地难度会集中在状态一致性和可观测性**上，而不是“能否写出算法”。

## 2. 方案一可行性（MHA 全息记忆 + b1.58 执行门控）

## 2.1 结论

**可行性：中等偏低（建议作为研究支线，不建议先作为主干）**。

## 2.2 与当前 zen-claw 的适配点

- 顶层 b1.58 执行门控与当前的 Tool Policy / Approval 机制理念一致，可以较低风险地接入到执行前置检查层。
- 但“全量历史不压缩 + 全局注意力检索”与当前的上下文压缩、max token、memory recall 模式是冲突的：现有系统默认把上下文控制当成稳定性前提，而非可选项。

## 2.3 主要风险

1. **延迟和成本会穿透控制面**：zen-claw 的 loop、路由、工具执行都在一个实时链路上；一旦 recall 从“候选召回”变成“全历史全量 attention”，会直接放大响应尾延迟。
2. **误召回会放大 Gate2/Gate3 负担**：当前路由契约假定输入噪声可控。若探针权重不稳，Gate2/Gate3 会承接大量伪相关上下文，导致“看起来更聪明、实际更不稳”。
3. **工程上难与现有压缩机制共存**：当前已有 `ContextCompressor` 与 token 阈值；方案一若坚持不压缩，会破坏现有保护带。

## 2.4 若要试点的最小实现

- 不改主链路，只加一个 `memory_recall_mode="mha_experimental"`；
- 仅对“只读意图 + 低风险工具”开启；
- 强制保留现有 max token 截断和超时熔断，禁止“全量历史硬穿透”。

> 结论：可研究，但不应作为第一优先主线。

## 3. 方案二可行性（b1.58 记忆库 + MHA 路由）

## 3.1 结论

**可行性：中等（可做，但需要强约束版落地）**。

## 3.2 与当前 zen-claw 的适配点

- 底层三进制检索可与当前 recall 插件化架构对接：可新增一个 `trit` 或 `hamming` 召回策略，不必重写 AgentLoop。
- 中间“柔性路由”与项目已有的 Gate2/Gate3 思路有天然亲和，理论上可以放到 `intent_router_classifier` 或 `orchestration` 的候选生成层。

## 3.3 核心问题

1. **信息折损与业务可用性冲突**：zen-claw 场景包含多渠道、RAG、工具调用参数；很多长尾细节（ID、时间、上下文限定词）不适合被强量化。
2. **路由黑盒化会冲击可审计性**：当前仓库大量测试都围绕“可解释路由 + 可预测执行”展开，过度柔性组合会让回归测试成本指数级上升。
3. **错误 API 调用风险真实存在**：若把创造力放在“工具链拼装”，而非“回答生成”，会直接碰到外部副作用风险（写库、发消息、执行命令）。

## 3.4 可控落地方式

- 把 MHA 路由限制在 **候选排序** 而非“自由拼装执行图”；
- 执行层继续走现有 `allowed_tools/denied_tools/approval_required` 契约；
- 对外部副作用工具保留硬性 deny-by-default。

> 结论：可以推进，但不能把“动态组合”直接下放到可产生副作用的执行层。

## 4. 方案三可行性（三明治：b1.58 检索 → MHA 规划 → b1.58 顶层门控）

## 4.1 结论

**可行性：高（在当前项目中最值得作为主路线）**。

## 4.2 为什么最贴合 zen-claw

zen-claw 本身已经是“多层控制”的架构：

- 底层：可插拔 recall / RAG；
- 中层：Intent Router + Gate2/3 决策；
- 顶层：Tool policy + approval + kill-switch。

这与“三明治”几乎一一映射，不需要推翻现有主干，只需把每层能力替换为更强版本。

## 4.3 关键挑战（真实且不可忽视）

1. **层间语义漂移**：中层认为 99% 可行，顶层规则判 -1 拒绝，若缺少统一错误语义，会出现反复重试。
2. **状态机复杂度上升**：现有 Gate 流程已不简单，再叠加量化检索与新路由，必须先统一 tracing 字段和失败分类。
3. **组织协作成本（在小团队可控）**：该风险在大组织更明显；对于当前轻量团队，短期可由统一 owner + 单一评测集压住，但随着模块和贡献者增长，仍建议提前固化公共契约。

## 4.4 建议落地顺序（按风险递增）

### Phase C（优先，约 2 周）：顶层 b1.58 安全门控增强

- 将敏感工具与关键参数映射到离散风险向量；
- 触发 -1 时必须给出结构化拒绝原因（用于恢复与重试抑制）；
- 与 ApprovalGate 合并成统一决策事件，避免双重判定冲突。

### Phase A（第二阶段，约 3~6 周）：底层三进制检索试点

- 新增 recall strategy（只替换 memory 召回，不动执行链路）；
- 离线对比：召回率、误召回率、**token 节省优先**，延迟收益单列观察；
- 明确记录当前向量后端是否将 `-1/0/1` 强转为 Float32，若是，则将“延迟收益”降级为远期目标；
- 只在低风险 profile 开 feature flag。

### Phase B（最后推进，定义为技术攻坚 Spike，约 6~8+ 周）：中层 MHA 候选排序

- 定位为独立 R&D 轨道，不按常规迭代 KPI 管理；
- 先做路由数据集建设（Query -> Candidate 正/负样本），再做模型选择/微调；
- 仅影响 Gate1/Gate2 的 candidate ranking，不允许越过现有 contract 直接生成执行计划；
- 增加“为何命中/为何未命中”证据字段，保障可审计；
- 若离线评测未显著优于“LLM 直接结构化路由”，则保持为实验特性，不进入默认链路。

## 5. 综合建议（面向你给出的三选一）

- **短期主推：方案三**（最符合 zen-claw 当前分层现实，收益/风险比最高）。
- **中期补充：方案二的“受限版”**（仅用于检索与候选排序，不放开执行拼装）。
- **长期研究：方案一**（保留在实验轨道，不进入默认生产链路）。

如果目标是“尽快在当前项目看到稳定收益”，推荐执行顺序为 **C → A → B**：

1. 先做 Phase C（先把顶层安全反馈回路做硬）；
2. 再做 Phase A（先拿到检索可控收益，优先看 token 与召回质量）；
3. 最后做 Phase B（作为中层软路由攻坚）。

## 6. 量化验收指标（建议）

为避免“感觉更聪明但系统更脆”，建议在 PRD 层预先锁定 6 个门槛：

1. P95 端到端延迟不劣化超过 15%。
2. 工具误调用率（含错误 API）下降或持平。
3. 人工审批触发准确率提升（减少无意义审批）。
4. 同问题重试次数不增加（防止层间打架）。
5. 可解释性字段覆盖率达到 95%+（每次拒绝/放行都有结构化原因）。
6. 回归测试稳定性不下降（关键路由测试通过率保持基线）。

---

## 最终判断

从“与 zen-claw 当前架构的贴合度、落地风险、可验证性”三者综合看，**方案三是唯一适合作为当前主干演进方向的方案**；方案二可以作为受限增强；方案一更适合作为研究型分支而非近期工程主线。


## 7. 对审阅意见的复核结论（2026-04-06 增补）

本次复核后，以下判断成立：

1. **“Phase B 时间被低估”是合理且关键的纠偏**。
   中层 MHA 即使只做 ranking，也涉及冷启动特征、数据集、评测与可能的专用路由模型，工程属性更接近“技术攻坚”而非普通迭代。
2. **“Phase A 基建适配成本被低估”同样合理**。
   在现有生态里，三进制向量常被上层接口包成浮点检索；短期更确定的收益是 token 与噪声过滤，而不是检索时延。
3. **“层间语义漂移”是核心一号风险**，并且保持原判：
   必须让 -1 拒绝输出结构化原因，作为中层重规划的抑制信号，避免无限重试。
4. **“组织协作成本”在当前团队规模可下调优先级**，但不应删除：
   现阶段可通过统一 owner + 单一评测集控制；当多人并行开发时该风险会重新抬头。

因此，本文将执行建议从原先的 A→B→C 调整为 **C→A→B**。
